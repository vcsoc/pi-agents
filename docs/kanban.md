# Project Kanban

The native Pi harness is always the operational home for pi-crew. Kanban is an optional managed task workflow and external live interface, off by default. With it off, manage agents directly through the native harness: no Kanban tools, new board access, task creation/dispatch, rubric assignment or managed acceptance handoffs. Report progress, blockers and results in concise, human-readable language; complete small work directly and avoid unnecessary handoffs and polling. Agent calls, workflows, ordinary tools, results, steering and the fleet remain available in either mode.

## Enable And Open

1. If the entire extension is off, run `/crew on`. Then open `/crew`, choose Settings, and turn **Kanban** on.
2. Run `/crew kban`. Pi opens a browser and also prints the private URL.
3. Ask the main agent to break your request into scopes, assign each task, define its acceptance rubric, and release the work.

To switch back to direct native-agent management, turn only **Kanban** off in Settings. `/crew on` and `/crew off` instead control the **entire pi-crew extension**, independently of Kanban. Master off withdraws all pi-crew tools, workflow prompts and live UI, stops active/queued agents and workflows plus scheduling, and disconnects routing/RPC while retaining records, sessions and evidence. Master on restores the saved feature preferences but never restarts interrupted runs. The project `extensionEnabled` flag is persisted; a save failure explicitly warns that the change is session-only. `/crew on`, `/crew status` and `/crew version` remain usable while the extension is off.

You can also set `"kanbanEnabled": true` in project or personal `subagents.json` and reload Pi. The setting controls the entire Kanban workflow, not only the web interface. Disabling it withdraws the orchestrator tool and its prompt guidance, suppresses board notifications and new task dispatch, and closes the local server. Existing workers retain their bindings and can drain their current checkpoint safely; their evidence is preserved, but follow-on roles do not dispatch while off. An idle disabled controller does not read the board. Re-enabling restores the tool and eligible dispatch without duplicating workers or restarting user-paused, suspended, cancelled or archived work. A trusted project is required for task-service activation.

The `Kanban` task tool is registered before an agent turn only when enabled in a trusted project. Disabled tools reject even stale calls. `/crew tasks` and `/crew kban` explain direct agent management when off and never initialize task storage. When enabled, the main agent can use the tool alongside ordinary tools, Agent and workflows; `/crew tasks` lists tasks and retained native runs without a browser. `/crew tasks pause <run-id>` explicitly stops one current native run, and `/crew tasks pause-all` pauses pending tasks, stops the local scheduler and cancels current native agents/workflows. These are deliberate cancellation controls, not effects of toggling the view. Paused task evidence is invalidated; existing native agent conversations can be explicitly resumed with Agent, and stopped workflows can be explicitly resumed through SubagentWorkflow. No automatic replay is promised.

Live Harness Runs shows the actual retained top-level agent/workflow records in this Pi session, including ordinary non-task work. Task planning/history is durable and project-shared; native run visibility is session-local and completed native records have the fleet's normal retention limit. Native runs are not fabricated into task-certified Done cards. Managed task workers still enforce their assigned capabilities and independent evidence gates.

## Task Lifecycle

| Column | Purpose |
| --- | --- |
| backlog | Capture scope, acceptance criteria, agent assignment, and rubric. No worker executes the task. |
| ready | Approved for its assigned operator to start or resume. |
| in progress | The operator implements the assigned scope. |
| review | The tester runs commands and scores the submitted revision; the reviewer independently reviews and scores it; the orchestrator performs final scoring. |
| done | Accepted work passed every completion gate, or obsolete work was explicitly closed with a `cancelled` disposition (not acceptance). Accepted tasks can receive read-only replies; cancelled tasks never dispatch. |

The orchestrator immediately prepares tasks using `Kanban create`, providing title, scope, project-specific best practices and rubric criteria. If no agents were requested, the operator defaults to `operate`. Each criterion has a descriptive title and a positive percentage weight; weights must total 100. `testerAgent` and `reviewerAgent` default to `operate`. These are independent worker sessions with separate role-bound capabilities, even when they use the same agent definition/model. Use `inspect` or `design` as operators for read-only scopes, and `operate` for implementation and executable testing.

Fully specified orchestrator-created tasks move immediately to Ready in the create call and trigger native dispatch, without a second release call. Only use `holdInBacklog: true` when the user explicitly requests a hold; clearly report the task ID, reason and `Kanban ready` action needed to initiate it. Creation still validates scope, assignments and a rubric totaling 100 before release; omitted best practices use the shared scoped-execution policy. User submissions and worker proposals initially enter Backlog for orchestrator preparation: immediately inspect/refine their scope, assign operator/tester/reviewer, set weighted rubric and best practices, then call `Kanban ready` in the same turn. Never stop at a creation acknowledgement or leave new work idle without an explicit user hold; report genuine blockers and request any required interactive launch approval immediately rather than bypassing it. Default execution uses three independent `operate` sessions (operator, tester and reviewer), not the read-only `inspect`/`design` definitions as implementation/test owners. Continue eligible work through the existing handoffs, repairs and final orchestrator acceptance until Done. Existing user pauses, dependency holds, run budgets and cancelled/archived tasks retain their gates and are not automatically resumed. The task-specific `KanbanTask` tool is injected into its worker, including isolated workers, and no worker may edit other tasks or delegate around the board. An operator calls `handoff` to submit work to testing. The tester calls `test` for actual commands, then `evaluate` with one 0-100 score per criterion, completes any required PR initiation, and hands off. The reviewer evaluates independently, performs its PR stage when required, and hands off to the orchestrator. The orchestrator uses `Kanban evaluate` and `Kanban complete`.

The following all block completion:

- Missing, below-85%, or outdated orchestrator, tester, or reviewer scores. Exactly 85% passes; percentages are not rounded up for gating.
- Missing passing test evidence, a failing latest execution of a recorded command, or a source snapshot different from the submitted revision.
- Incomplete configured PR review/merge or failure to publish all three evaluations to the PR.
- A paused, archived, reassigned, stale, or otherwise invalid task run.

A tester can give a below-threshold evaluation after a failed test; it must include precise repair instructions. The evaluation and test output remain in task history, a clear comment is added, current scores are invalidated, and the operator receives the task in ready. Reviewer or orchestrator rejection follows the same repair cycle.

Tests execute with a ten-minute command timeout and record command, exit code, bounded output, timestamp, and source fingerprint. Repeating the same command replaces its current result while preserving prior runs in history. Tests that modify source must be followed by resubmission and fresh testing, not certification of a different revision. Source fingerprints exclude private Pi/vault state, dependencies, and generated dist/coverage output. This verifies what was executed against which source snapshot; agents are still responsible for choosing meaningful tests and honestly evaluating the rubric. A successful `true` command is not a substitute for project-specific acceptance tests.

## One Execution Owner And Linked Work

Only the assigned operator with the current native lease/identity may implement the task artifact scope. Independent testers/reviewers assess; they do not become implementation owners. Their ordinary tools are limited to inspection and `KanbanTask`; the tester executes validation through `KanbanTask test`, which verifies the submitted fingerprint before and after execution. Arbitrary shell, edit/write, deferred mutation tools and delegation are refused for assessment roles. These are cooperative native tool capabilities, not an operating-system sandbox: validation commands still have local process permissions and must be selected responsibly. Source-mutating validation is rejected, never accepted as a repair. Have the operator repair, or propose separately owned linked work.

A worker uses `KanbanTask propose` with a `proposal` object containing `parentId`, `title`, bounded `scope`, `reason`, `expectedResult`, and `relationship: { targetId, type, blocking }`. Both IDs must identify that worker's assigned parent. The service atomically validates the relationship, creates an unassigned Backlog-only child with no rubric, and notifies the orchestrator. No agent is started or permission granted. The orchestrator alone immediately refines the child with `Kanban edit`, assigning `assignee`, weighted `rubric` and explicit `bestPractices`, then releases it with `ready` in the same turn unless the user explicitly requests a Backlog hold. Clearly report such holds and the release action to the user. Use links for genuinely separate ownership, not pointless fragmentation.

Relationship direction is always **this task to targetId**:

| Type | Direction | If blocking |
| --- | --- | --- |
| `depends-on` | This task needs target's result | Target must be accepted Done before this task runs. |
| `completed-after` | This task follows target | Target must be accepted Done before this task runs. |
| `completed-before` | This task precedes target | This task must be accepted Done before target runs. |

`blocking: false` is informational ordering only: it does not suspend, restart or authorize execution. Informational cycles are permitted because they cannot deadlock dispatch; changing such links to blocking is revalidated and any executable cycle is rejected. `Kanban link` lets the orchestrator replace a task's `links` array; invalid/self references and blocking dependency cycles fail atomically. Legacy tasks without link fields retain their existing lifecycle.

A newly unmet blocking prerequisite suspends an active parent checkpoint by revoking its tool lease, not resetting its revision, source snapshot, fingerprint, evidence or audit history. The native worker is stopped and its execution-drain fence retained until it actually settles. Runtime-completed and cancelled children do not satisfy prerequisites: accepted Done requires all three current >=85 evaluations and current passing test evidence. Satisfied prerequisites produce a notification, never automatic dispatch. The orchestrator explicitly calls `ready` to continue an eligible suspended checkpoint only after draining; normal role, source-fingerprint, isolation, run-budget and acceptance gates remain in force. Manually paused, archived and cancelled tasks never auto-restart. Explicit continuation reconciles source-changing accepted prerequisites into a **new** parent snapshot, leaving the retained original workspace and its evidence intact. Only caller changes whose bytes/modes match accepted prerequisite results are eligible; unrelated caller changes, stale child fingerprints and any overlapping parent/prerequisite paths are refused before publication. Disjoint parent edits (including additions, deletions and modes) are carried forward onto the new caller baseline. A changed composition increments the parent's revision, returns it to its assigned operator, and clears current tests/fingerprint/evaluations, retaining their full previous values and workspace paths in audit history. The combined source must be resubmitted and independently tested/reviewed/scored again. Unchanged source continues the suspended phase/revision without invalidating its evidence. PR worktrees are not automatically rebased by this non-PR snapshot reconciliation.

## Snapshot Fixtures And Dependencies

Snapshot transport continues to exclude every `.pi`, `vault`, `node_modules`, `.git`, `dist` and `coverage` component. Genuine end-to-end templates and skills are tracked under `test/fixtures/runtime-config/`; the tests materialize them into an ignored disposable `.runtime-*/.pi` directory, then remove it. No private history is transported or replaced with dummy fixtures. Snapshot regression tests compare the complete real fixture tree byte-for-byte, and explicitly test tracked private-path exclusion.

Dependencies are deliberately not inherited or symlinked from the caller. For this repository, run `npm run snapshot:preflight` in the snapshot before testing. This read-only check verifies direct dependency versions against `package-lock.json`, checks the offline dependency tree, and reports Node/npm versions and lock SHA256. If dependencies are missing, **obtain installation authorization first**, then run `npm ci --ignore-scripts --no-audit --no-fund` in that snapshot and repeat preflight. This lock-based preparation does not rewrite Pi/user settings. Packages requiring lifecycle builds need separately approved project-specific preparation; preflight never silently installs or runs lifecycle scripts. Other projects need their own lock-based preparation, not an assumption that omitted `node_modules` exists.

## Fast Scoped Execution

Orchestrators and workers share this policy: complete the assigned scope as quickly and efficiently as possible, ideally within 15 seconds for small, well-defined work. Minimize unnecessary tools, exploration, duplicate work, polling and handoff delays. Stay strictly within scope and follow stipulated best practices. Report blockers promptly and propose linked work when another execution owner is needed. Use the shortest safe implementation and validation path. Fifteen seconds is aspirational, not a hard timeout or guarantee; do not fragment work pointlessly. Speed never permits bypassing acceptance gates, concealing errors, weakening safety or introducing avoidable risk or technical debt. Report runtime separately from verified acceptance.

## Explicit Cancellation Without Acceptance

Use the orchestrator's `Kanban` tool with `action: "cancel"`, the task `id`, and non-empty `notes` explaining why the scope is obsolete. The authenticated user API also supports `POST /api/action` with `action: "cancel"`, `id`, `reason`, and the current `expectedUpdatedAt`. These controls work on unfinished, unarchived tasks; a successful accepted completion cannot be relabelled as cancellation. Task content or comments saying "cancel" do not authorize a worker to do so. Only the user or harness orchestrator can invoke this action; worker-bound `KanbanTask` has no cancellation capability.

Cancellation moves the card directly to Done and persists `disposition: { kind: "cancelled", reason, actor, at }`, plus a `cancelled without acceptance` audit event recording its previous column, phase, revision and revoked lease. It does not call `evaluate` or `complete`, invent scores, mark tests passing, integrate source, publish a PR, or certify acceptance. Existing evaluations and failed/passing tests remain exactly as recorded, with all comments, history, fingerprints, PR metadata, snapshots, private worktrees/checkpoints and run budgets retained. Legacy Done tasks without this disposition still use the existing accepted-completion semantics; the virtual demo board remains separate and read-only.

The action revokes the worker's tool capability immediately and requests abortion of its local native run. Other Pi sessions reconcile the revoked lease on their next tick; later tool calls fail closed. Execution-drain leases remain until the original worker actually settles (or its process is confirmed dead), so cancellation or subsequent archiving cannot prematurely free cross-process capacity. No filesystem edits or remote side effects are undone, and detached external processes cannot be guaranteed to terminate.

Cancelled tasks are terminal: comments remain available as history but never spawn read-only replies, and Backlog/Ready cannot reopen or reset their retained evidence. Create a new scoped task to authorize new work. Repeating cancellation retains the original reason and audit record rather than rewriting it. Cancelled Done cards can be archived normally without deleting their disposition or evidence. Pausing in Backlog remains the distinct, resumable edit/rework path and still invalidates current acceptance evidence. Cancellation is an honest closure outcome, never a substitute for managed-task acceptance or permission to weaken its gates.

## Audit Contention Recovery

Every worker observation is written ahead to a private durable outbox with stable IDs/timestamps. A typed `KanbanBoardBusyError` is transient: synchronous capability checks may defer delivery of already durable observations, and concurrent task tools share one bounded audit drain (initial attempt plus three retries at 25/50/75 ms). Persistent contention returns a retryable error without advancing handoff or losing events; native polling retries later without overlapping dispatch. Test commands themselves are never replayed merely because evidence publication contends. Acknowledgement loss replays the same IDs and the store deduplicates them. Genuine persistence, capacity and storage failures continue to block tools/handoff and retain recovery evidence. Revoked worker cancellation/abort always happens before audit draining; temporary contention never authorizes resuming a paused/cancelled task. No live outbox or lock is deleted as a recovery shortcut.

## User Controls

The fixed topbar contains tooltip-labelled icon actions for Add, Pause all, Archive completed scope, native Harness visibility and persisted day/night theme. The archive visibility control is a keyboard-accessible switch. The title's focusable information icon contains live progress and the complete edit/resume/card-actions/Done-only archive guidance. Created task-agent pills below the topbar expose their role, task-worker state and reason: orange active, red blocked/error, green completed, grey idle; native harness runs remain separately labelled session status. Pill color is never the only state indication. The harness panel explains that Pi owns execution and web visibility never stops work.

Columns fill the remaining viewport with distinct theme-compatible backgrounds and independently retained scroll positions; narrow displays scroll the columns horizontally, keeping controls and headers available. Task dialogs offer Scope, Evidence and Execution tabs with arrow/Home/End navigation and selected-tab semantics. Conversation stays docked at desktop widths and is reachable below the tab content on mobile. Icon actions retain their permission gates and confirmation prompts. Deliberate pointer-down/click on the backdrop closes a dialog; internal clicks and drags beginning inside do not. Escape, focus restoration, comment drafts, expanded evidence and live-update selection remain supported.

- Add task submits a title, scope, operator and project-specific acceptance criterion to Backlog and notifies the harness orchestrator. It does not start work or accept forged scores. The orchestrator immediately reviews/refines assignments, best practices and weighted criteria, then releases it to Ready in the same turn unless the user explicitly requests a hold. Required approvals remain binding.
- Live Harness Runs shows native status, with Pause run for active agents/workflows. Pause all work pauses pending managed tasks (including in other Pi sessions sharing this board) and stops current native agents/workflows and scheduling in this Pi session. It does not control unrelated native runs in other Pi processes. Resume deliberately through the harness or individual task Ready controls.
- Click a card to open the complete task modal, including comments, independent evaluations, test results, PR link, and audit history.
- Add a comment to steer the currently running assigned worker. It is retained for subsequent roles. Idle completed tasks can dispatch a read-only response from the assigned agent; a comment alone never authorizes implementation changes.
- Drag a task to backlog or choose Pause in backlog to invalidate its active run and evidence. Edit its title, scope, assignment, and rubric, then save. Release to ready after editing. An orchestrator cannot silently release a task you paused.
- Only backlog and ready accept manual column changes. Dragging straight to review/done cannot bypass testing or scoring.
- Archive is available only for Done tasks, from the context menu or modal. It retains history and prevents future task/comment-response dispatch. For unfinished work, pause in Backlog to edit/resume later, or explicitly cancel obsolete scope through the harness tool/user API to close it as Done without acceptance. None of these actions undo filesystem edits, commits or PRs.
- Archive completed scope becomes available when every non-archived task is done. Show archive makes historical tasks visible again. Comments can document cancellation, but never resume archived work.
- Approve PR merge is available only for merge-policy tasks. It grants that task's reviewer permission to attempt the merge after passing gates. Scope changes/rework invalidate previous merge approval.

Closing a browser tab does not stop workers or disable dispatch. Disabling Kanban preserves existing workers but stops new task dispatch and switches the main agent to direct native-agent management. Moving unfinished work to backlog or explicitly pausing runs requests cancellation; actual session shutdown still stops workers and releases resources. Cancellation blocks later managed-task tool calls and requests abortion of in-flight work; it cannot undo already-performed filesystem/network effects or guarantee termination of independently detached external processes.

## PR Policies And Git

The orchestrator chooses `prMode` from the user's request and repository instructions:

| Mode | Required behavior |
| --- | --- |
| none | Work in private source snapshots with conflict-checked integration; no GitHub operations. |
| review | Tester creates/pushes a PR and records tests/scores; reviewer publishes a review and verifies required CI. Leave merge to the user/project process. |
| merge | Same testing/review steps, plus explicit user merge approval and a verified completed merge before done. |

PR tasks require a Git repository with an initial commit, an `origin` remote pointing to the intended writable repository, and authenticated `gh`. Task worktrees start from committed HEAD: existing tracked project changes must be committed first, and untracked files are not copied. Subfolder projects retain their relative location inside the task worktree. The task gets a persistent external Git worktree on `pi-kban/<task-id>`; operator, tester, and reviewer share that task worktree. The operator must commit its changes on that branch and leave it clean before submitting. The tester pushes the branch, opens or updates its PR, and includes the task scope, weighted rubric, test evidence, and tester score. The reviewer checks required CI, publishes its independent review, and performs the configured PR stage. The final PR body is updated with all three scores before the task becomes done.

Agents normally share the same GitHub credential. The reviewer posts a comment review identifying its role; the extension does not pretend that this is an approval from a second GitHub account. Required human approvals and other branch protections still apply. Merge uses the expected head commit, never `--admin`, and is considered complete only after GitHub reports `MERGED`. Authentication, permission, missing required-check configuration, head changes, pending approvals, or merge failures stay visible instead of being marked done. A reviewer waiting for merge permission pauses; approving from the board allows the PR stage to resume.

PR worktrees and task branches are retained for inspection/rework; archiving does not automatically remove them. In review-only mode, done means the requested PR/testing/review scope is complete, not that the branch has merged into the original checkout. Even after a remote merge, the original local checkout is not automatically pulled.

Non-PR managed tasks run in private source snapshots, subject to the configured native background pool and cross-Pi leases. Tests and all three evaluations must certify the same source fingerprint. Completion serializes integration and refuses changed caller baselines (even disjoint changes), dirty/untracked caller paths (including staged edits masked by working-tree bytes equal to HEAD), private collisions and changed submissions; resubmit/retest instead of overwriting. Git branch/index are preserved. Recovery journals and original/displaced inodes may remain in private sibling directories even after success; inspect the reported recovery path and clean up only after editors release their descriptors. This is trusted-process isolation and synchronous failure recovery, not an OS sandbox or crash/power-loss-durable multi-file transaction. Writable same-filesystem sibling storage is required. Pausing retains snapshot evidence and does not revert edits. PR tasks use separate worktrees under the same native capacity constraints. Direct Agent/workflow work remains supported; it is not implicitly managed-task-certified and its caller-source changes can correctly cause a pending task integration conflict.

## Persistence, Budgets And Failure Recovery

The board name is the canonical project folder's basename. Its ID is the SHA-256 hash of the canonical absolute folder path, so symlinked paths share a board and equally named folders in different locations do not. Moving a folder changes its ID; boards are machine/path-specific rather than a cross-machine sync service.

State lives at `<Pi agent directory>/kanban/<project hash>/board.json`, outside the project and Git history. Writes use an exclusive process lock and atomic replacement. Task comments, transitions, tests, score evaluations, archive records, and failure reasons remain in history. Source revisions and role-bound run tokens reject stale workers. Different Pi sessions share the same durable state and cannot claim the same live task twice.

Default limits are 12 worker runs per task and 40 turns per worker run. The orchestrator may set `maxRuns` between 3 and 100 at creation. These runs incur normal provider costs; there is no implied monetary cap. Automatic repair attempts consume the same run budget. An exhausted budget is visible and blocks more runs until you move the task through backlog then ready to authorize a new budget. Orchestrator requeues do not reset a used budget. Test command output is truncated to the last 16,000 characters in current evidence; complete command output should be preserved separately when required by the project.

A worker that ends without a valid handoff becomes blocked rather than silently retrying. Read its transcript and task evidence before retrying through backlog/ready. Session shutdown marks interrupted work blocked; restarting Pi does not blindly replay a half-finished command. A lease from a process that no longer exists can be recovered. Corrupt state is reported, not silently reset. Back up the state directory for long-term history retention.

## Web And Trust Boundary

The server binds only to `127.0.0.1` on a random available port. Board APIs and the live SSE stream require a random bearer token, supplied in the browser URL fragment and retained only in that browser session. Requests with unexpected Host/Origin headers are rejected; API mutations require JSON, a matching task version, and bounded payloads. The frontend uses no third-party scripts/assets, renders task data as text rather than HTML, and reconnects its live stream after interruptions. Keep the private board URL private.

Kanban gates govern cooperative agent sessions in this extension. They are not operating-system sandboxes, GitHub authorization boundaries, or protection against arbitrary trusted extensions or a malicious process with filesystem access. In particular, a full-tool operator/tester still runs with your local permissions. Use repository review, normal GitHub protections, and external sandboxing where stronger isolation is required.

## Validation Commands

Run `npm run check` for lint/typechecking/unit and integration tests. On a heavily loaded machine, `npm test -- --maxWorkers=4` avoids contention with the existing workflow metadata evaluation time limit.

`npm run test:kanban:ui` builds and drives a real local Chromium through its debugging protocol, exercising live updates, desktop/mobile rendering, modal edits, comments, drag/drop, and archive controls. Install Chromium or set `CHROMIUM_BIN` to a compatible Chrome/Chromium executable. Set `KANBAN_UI_ARTIFACTS` to choose the screenshot directory; otherwise it uses a temporary directory. The fixture never releases real model work or creates a real GitHub PR. PR integration tests use local Git worktrees and simulated GitHub responses.
