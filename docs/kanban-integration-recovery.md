# Accepted dirty-source integration recovery

`Kanban complete` now recognizes dirty paths that are **already exactly accepted integrated results**, not arbitrary user edits. No new user configuration, manifest edits or blanket override exists.

After all existing completion gates pass and while holding the board lock, integration performs a read-only lookup of the adjacent private board. The target must match project, workspace, manifest, revision and submitted fingerprint, be drained in Review/orchestrator, and have current passing evidence and three >=85 evaluations. No store/controller change is needed. Eligible provenance must have accepted Done state, all three current >=85 evaluations, passing current tests, a revision-matched retained snapshot, and a publication audit listing the exact path and accepted fingerprint. Integration rechecks that retained source fingerprint, that the accepted task actually changed this path, and that accepted bytes/mode exactly equal the protected baseline. Staged protected paths are conservatively refused, including staged changes masked by working bytes. Ordinary baseline/caller comparisons and concurrent-save/no-clobber recovery remain unchanged.

The protected manifest is never modified. Each authorized path and full provenance (task ID, revision, fingerprint, manifest, workspace and published paths) is recorded in the retained recovery journal, linked from the existing completion recovery audit. A detached manifest or unassessed target has no authorization. Integration remains an internal synchronous API that must run under the existing store completion lock; no mutable global authorization or user-facing bypass is added. Cancelled/unaccepted results, stale evidence/source, absent or mismatched publication, unrelated dirty bytes, and caller changes remain blocking. An exception does not certify renderer preservation semantically: independent review/tests still must validate the composition.
